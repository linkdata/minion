# linkdataminion

[![build](https://github.com/linkdata/minion/actions/workflows/build.yml/badge.svg)](https://github.com/linkdata/minion/actions/workflows/build.yml)
[![coverage](/../gitcoverage/main/badge.svg)](https://github.com/linkdata/minion/tree/gitcoverage/main)

A small Go service that watches a bot account's GitHub notifications in an explicit repository whitelist for commands. It invokes the authenticated Codex or Claude CLI for the work and uses Git and the GitHub API for publication. The checked-in [config.json](config.json) contains sample settings; copy it to the ignored `config.local.json` for a real deployment.

## Goal

Minion should start one AI-assisted action from a configured command, without free-form instructions in the command. Only collaborators with write or stronger access should be able to request work, and only in repositories explicitly selected by the operator or automatically registered from invitations by pinned owners. GitHub text and repository files are untrusted input; the default anti-prompt-injection skill should help the models keep them separate from operator instructions. AI-assisted work should run in sandboxes. Application logic, rather than AI instructions, should choose and limit GitHub operations, destinations, and publication states.

The security boundary is the operator-controlled configuration and mechanical checks on repository scope, requester permissions, and permitted actions, together with the AI CLIs' native sandbox restrictions and application-controlled GitHub writes. Minion requests sandbox modes; each CLI enforces its own restrictions. These controls must hold even when the model follows an injected instruction. [Deployment isolation validation](https://github.com/linkdata/minion/issues/7) remains a public-release follow-up.

The embedded `builtin://anti-prompt-injection` skill is enabled by default for both model roles. GitHub titles and descriptions are quoted as untrusted task data in model prompts. Quoting and skill instructions are best-effort defenses against prompt injection; they do not enforce the security boundary. The skill tells each model to use untrusted content as evidence for the selected task, including relevant requirements and prior decisions, without letting instructions inside it change the selected action, authorization rules, permissions, publication destination, or publication state.

Minion does not use a separate prompt-injection classifier: the operator judges its false refusals and operational complexity to outweigh its benefits ([decision #86](https://github.com/linkdata/minion/issues/86)).

## What it does

The defaults below use `@linkdataminion`; substitute the configured `bot_login`. The `commands` mapping defines the available names and AI skills; each repository's `actions` list selects which names it accepts.

| Command | Result |
| --- | --- |
| `@linkdataminion review` | On a pull request, the main model uses the ponytail-review skill to review its exact head against its base. The bot submits a comment review; it never approves. |
| `@linkdataminion fix` | On an issue, the main model uses the ponytail skill to edit a pinned checkout of the default branch. The bot pushes a deterministic branch to its own fork and gives the requester a compare link to open the pull request themselves. |
| `@linkdataminion audit` | On an issue or pull request, the `comment` action uses the ponytail-audit skill for a read-only source audit and posts its report in the requesting thread. |
| `@linkdataminion security-audit` | On an issue or pull request, the main model uses Cloudflare's security-audit skill. The bot validates its report artifacts and posts the findings summary in the requesting thread. |

Every action supplies a usable local Git repository with complete history, including historical file contents, branches and tags. Models can inspect local history through the supplied `.git` metadata. Remote-tracking refs such as `origin/<name>` remain visible; pull requests also have `refs/remotes/minion/pr-head`; no remote is configured and no GitHub credentials are supplied. Minion does not authorize model fetches or publication; the orchestrator performs authenticated GitHub writes. Symlinks and submodule working trees remain omitted as declared in `source.json`; symlink blobs and gitlink entries remain in history. External LFS objects and other submodule repositories are not included. Pull requests retain pinned comparison context. History transfer is subject to the complete-bundle limit in [Action boundary](#action-boundary).

Fix replies record the expected branch head. Before enabling `fix` for a repository, create a fork under `bot_login` with the same repository name, disable GitHub Actions on that fork, and verify that no external CI, webhooks, or installed apps run its branch pushes with privileged credentials. Minion verifies the fork's parent and visibility, checks that its Actions are disabled, and refuses private fork PR settings that send base secrets or write tokens. The bot credential needs access to the base repository and its private fork PR settings; if the fork or settings cannot be read, `fix` does not publish; retries follow the [failure policy](#failure-policy). Private fork PR workflows may need to be enabled on the base repository to run CI after the requester opens the PR; keep secrets and write tokens disabled. Review any base `pull_request_target` workflows before enabling `fix`: that trigger can receive base credentials and must not execute untrusted fork-head code. Minion cannot prove that those workflows or external CI are safe.

The requester must open the pull request from their own account after reviewing the diff, so GitHub can apply any independent-review rule to that requester. The branch remains mutable afterward; protect `minion/fix-*` in the fork from updates by other writers and compare its current head with the recorded commit before merging. This private repository's current plan cannot enforce those protections or required reviews, so a second-person review remains a manual requirement here.

Before generating or pushing a fix, Minion reads effective push rulesets on the fork, monitored repository, and fork-network root. It allows active push rules only when GitHub exposes an explicitly empty bypass list, so the bot cannot bypass a restriction another fork would enforce. An unreadable or incomplete ruleset response prevents fix publication. An HTTP 403 before model work follows infrastructure retry/backoff without consuming an attempt or guaranteeing a reply; a 403 on the pre-push recheck is a publication failure. A saved complete result retries publication without another model attempt; an unsaved failure follows the failure policy. GitHub currently returns 403 for this private repository's rulesets on its plan, so fixes keep retrying until a trustworthy result is available. Branch rulesets on a base repository do not apply to its forks; push rulesets and their root bypass permissions do.

Each request must come from an account with effective repository `write`, `maintain`, or `admin` permission. An optional `allowed_actors` list narrows that group. Only the first nonblank line can start a command, with no inline arguments; a command inside a quote, fence, HTML comment or indented code block cannot start one. A later line that is exactly an enabled, installed command makes the request ambiguous, even inside a fence, HTML comment or indented block; `>`-quoted lines do not count. Inline arguments and ambiguous directives receive no bot reply; ambiguities are logged. Notes after an authorized command reach the main model as quoted task guidance within the selected action; they cannot change the bot's application-enforced limits. A review also includes the pull request title and description as untrusted context, even when the pull request author cannot run Minion. Fixes and audits use relevant thread descriptions as untrusted context. The bot checks the whitelist and command author's permission again before every action.

`max_github_context_bytes` limits the combined UTF-8 bytes of trimmed title, description, and requester notes included in an action (32 KiB when omitted or 0; configurable from 1 to 67,108,864 bytes). It counts these fields before prompt quoting, not the complete model prompt or repository files. Text at the limit passes this check; a larger total gets a fixed refusal before either model starts. Titles for the `review`, `comment` and `security-audit` actions exceeding the [action title limit](#action-boundary) before trimming get the same refusal. `fix` omits the title and counts GitHub's rendered issue text. Notes supplied in an issue or pull request body also count as part of its description. Shorten the text and post a new command.

Edited command sources are ignored. Post a new comment to request work after editing text.

Before generating or pushing a new `fix`, Minion reads GitHub's rendered issue text and checks the issue's edit time against the request. If the issue changed at or after the request, it refuses new work; review the current issue and post a new `fix` comment. A previously pushed branch remains available if publication later fails. With a saved complete result, Minion can reconcile its recorded SHA and retry the reply without rerunning the model; otherwise operator reconciliation may be needed.

After accepting an authorized command, the bot adds a 👀 reaction to the exact issue, pull request, comment, or review that contains it, before starting the main model. If the reaction fails, the selected worker mode retains the original acceptance and retries after the recovery poll interval; in-process mode retries the command through the pending-notification backoff.

An enabled command used on the wrong supported thread type gets a fixed reply; see the commands table.

The `security-audit` action requires Codex as main, with Cloudflare's skill, the standard profile, independent agents, and its six-phase reporting workflow. With Claude as main, commands mapped to this action are disabled at startup and ignored without a reaction or reply. Claude can serve as its critic. Source remains read-only; validated report artifacts return as data and are retained in a new directory under `work_root/audits/`, with its path logged in `journalctl`. Returned audit metadata identifies the target as `owner/repository@commit` rather than an executor-local path. The GitHub reply includes the audited commit and a parent-rendered summary of structured findings and coverage, not a downloadable attachment. Retained Markdown is executor narrative for the operator, not the text posted to GitHub or a mechanically verified account of the audit. Audit agents are instructed to inspect source and use the skill's report validators, leaving repository code, builds, tests, fixtures and live services unexecuted. The sandbox permits local commands, so the source-only execution rule currently relies on those instructions. Minion checks the validator scripts and Node's permission model before invoking the audit model, then runs the validators under those restrictions: file reads are limited to the installed skill and copied validation files, child processes are denied, and the environment has a scratch `HOME` and restricted `PATH`, plus the profile, temp and system-root variables needed on Windows. The publishing host independently runs its installed validators on copied report data before retaining a complete audit or posting a reply. Node 20–24 does not restrict network access through this model, so the installed skill source on both hosts must be trusted. Claims needing runtime evidence remain `needs_validation`. Agent IDs, review coverage and completion in returned artifacts are executor claims; the publishing host checks their structure and cited paths against the assigned source, not whether a separate reviewer actually ran. Audit agents are instructed to disclose missing tools or time limits as incomplete coverage. `max_runtime_minutes` caps the action; expiry cancels the direct executor command and cleans its workspace. Collected partial audit artifacts are labelled incomplete and are not published. Validator errors identify the failed script and exit cause without copying report-derived stderr into the journal.

Complete `REPORT.md` must contain non-ignorable text, including when it is only a code sample. The publishing host validates structured findings and coverage against the assigned source, then renders the public summary from those records. The installed skill asks agents to fill applicable detail Markdown files, but their emptiness does not block publication: the structured records carry evidence, blockers and validation plans, while nonempty prose would not establish that the detail is true. The host does not infer truth from free Markdown prose.

## Failure policy

A failed request gets at most three execution attempts, with these exceptions. The table distinguishes another execution attempt from replaying publication of a saved complete result. Exceptions require parent-observed facts or direct in-process Runner errors. An HTTP worker's failure classifications are diagnostic claims; a conclusive failed outcome consumes an attempt unless the parent has proved an exception.

| Failure | Policy |
| --- | --- |
| Unknown execution or outcome, including joined cancellation, URL transport or response-body read/decode errors | No further attempts; never automatically repeat paid model work. |
| Graceful SIGINT/SIGTERM cancellation before an acknowledged model call; unsafe work-root admission; executor workspace preparation EACCES/EROFS; GitHub API HTTP 401/403/408/429/5xx or request transport errors (`*url.Error`) before publication | Unless a model-call start was acknowledged or execution has an unknown outcome, retry on later polls without consuming an attempt. An unsafe-admission request stays queued without a failure reply until admission passes. A local worker lost before assignment delivery also refunds its attempt; loss after delivery has an unknown outcome and is not retried. |
| Action timeout; unsupported or oversized source; executor workspace preparation (directories, source/context/repository materialization, private index) or initial review-evidence save failure, except missing executables, EACCES/EROFS, or ENOSPC/EDQUOT; source-root anchoring failure; invalid job, prompt, main proposal, critic verdict or result; invalid collection/import or audit report validation; oversized model/fix output; supplied Git metadata or frozen critic input mutation; critic snapshot/review-history preparation failure after model work; unfinished critic reviews; a fix producing no commit; post-call usage failure; invalid or conflicting private evidence or retained audit content | No further model execution attempts. A saved result can retry only the publication and storage failures below. |
| Other provider, missing executor Git, Git transport, audit-tool prerequisite, response-body read/decode or initial/pre-call usage save failures; executor workspace preparation or initial review-evidence save ENOSPC/EDQUOT | Unless a model-call start was acknowledged, consume an attempt. Fixed replies and refusals follow the pre-publication rules. |
| Commit, push or publication failure after an acknowledged model call, without a saved complete result | No further model attempts; retain the failure and post the fixed failure reply. A pushed fix branch may remain available for manual recovery. |
| Retryable publication failure with a saved complete result, such as a GitHub reply error or an unavailable publishing audit validator | Retry publication from the saved result after source revalidation, including after restart. Never rerun the model. Each recovered publication call has its own `max_runtime_minutes` cap; source revalidation happens before that cap. If a recorded fix branch cannot be found, rebuild it from the saved source and result, then push only when its commit SHA and review decision match the checkpoint and the branch is still absent. A mismatch stops recovery for operator inspection. |
| Host I/O failure while retaining private worker diagnostics, review evidence or a completed audit after a complete result was saved | Retry retention and publication from that result after storage recovers; never rerun the model. An existing completed audit directory that differs from the saved result also retries for operator inspection; other content or integrity mismatches remain terminal. |
| Permanent publication error with a saved complete result, such as a fix that produces no commit | Stop publication retries and post the fixed failure reply without rerunning the model. |
| Final usage save failure after successful publication | Log a warning and retain the last durable counters; the published action stays successful. |

A saved result keeps its action accepted, so new notification discovery stays paused until publication succeeds or the action is otherwise resolved. A persistent publication failure can leave discovery paused indefinitely and require operator intervention. Source revalidation discards the saved result without a reply if the source or repository is no longer eligible, including an edited or deleted command, lost requester access, an archived or default-branchless repository, or a changed allowlist.
If an existing completed audit directory differs from the saved result, recovery keeps that directory and retries; inspect it before removing it to let publication continue.

Minion waits for each direct command to exit and bounds pipe draining. The AI CLIs own their model-tool processes. Minion does not track their descendants or enforce per-command process and memory limits. Run Minion inside a VM or container if hard resource isolation is required.

Before acknowledging a model-call start, the orchestrator saves a no-repeat marker with the job attempt. After that acknowledgement, Minion never automatically repeats model execution, including after service restart. A selected worker's complete result is saved before its upload is acknowledged; publication can retry from that result without another model call. Without a saved result, a failed assigned action is terminal and the requester can post a new command after inspecting the failure. An untrusted worker cannot make its own error flag decide whether to repeat paid work.

Before an acknowledged model call, when the service context is canceled and execution returns `context.Canceled`, that interruption refunds the attempt even if the error also carries `ErrTerminalJob`, unless execution has an unknown outcome. An action-only timeout or internal cancellation still consumes an attempt. After default signal handling is restored, another signal can terminate shutdown immediately; normal crash/hard-kill accounting then applies.

A complete selected-worker result received after cancellation is refused, even if the original deadline has not passed. The worker receives no success acknowledgment; the selected worker is quarantined and the service exits for its supervisor to restart it. A saved result can replay publication only while the original deadline remains open and no terminal decision has been recorded.

Minion posts a fixed reply after terminal failure or exhausted attempts. For a selected action, source and requester revalidation has a 150-second budget before a new reply. Repository identity lookup and comment posting each get a separate 10-second budget. After three failed comment posts, it logs the request URL and moves on. Repository lookup or identity-verification failures retry without consuming the comment-post budget. Post a new command after fixing the cause.

## Setup

Minion runs on Linux, macOS, and Windows. Linux and macOS allow Codex or Claude roles. On native Windows, [Claude cannot sandbox commands](https://code.claude.com/docs/en/sandboxing), so the required CLI setting `failIfUnavailable` makes it exit; configure Codex roles or run Claude inside WSL2. Minion does not gate Claude by OS or inspect its sandbox dependencies. CI runs Go tests, vet and build on macOS and Windows. It does not verify the installed AI CLIs' runtime sandboxing or login; validate those CLIs on the deployment host. The included systemd unit and shell scheduler example are for Linux/Unix hosts, not Windows.

Install Go 1.27 or newer, `gh`, Git 2.45.1 or newer, and the CLI for each enabled model role on the host that will run the service (`codex` by default). The selected CLI must be able to run Git and its helpers; Minion's host Git check does not prove access from model tools. Security audits also need Node.js 20 or newer on both the executor and publishing service host for the [permission model](https://nodejs.org/download/release/v24.20.0/docs/api/permissions.html) used by the skill's report validators, plus a main model with sub-agent support for that skill. Minion selects the supported permission flag at runtime. Keep configuration and saved provider credentials outside source snapshots and role runtime directories, and protect them with host account permissions. Minion filters credential variables from model-command environments but does not prove that host files are unreadable to model tools. Copy the sample configuration, set its bot login and repository whitelist, then authenticate as that bot in the same operating-system account or service environment. Add `invitation_owners` only if the bot should accept invitations from those owners:

```sh
cp -n config.json config.local.json
chmod 600 config.local.json
# Edit config.local.json before continuing.
gh auth status
# If codex.api_key is empty, verify the existing login:
codex login status
mkdir -p bin
go build -buildvcs=false -o bin/minion ./cmd/minion
./bin/minion -config ./config.local.json -install-skills
mkdir -p var/work
chmod 700 var/work
./bin/minion -config ./config.local.json -check
```

On native Windows, use PowerShell to copy the config, create `bin` and `var/work`, and run `go build -buildvcs=false -o bin/minion.exe ./cmd/minion`; then run `bin/minion.exe` with the same flags. Install the standalone `codex.exe`; npm's `codex.cmd` launcher cannot be started directly by Minion. The Codex CLI selects and enforces its native Windows sandbox backend; Minion requests a read-only or writable workspace. An elevated backend may allow broad same-user reads, including saved credentials, so choose the service account and host with that access in mind. CI runs Go tests, vet and build on Windows x64; it does not exercise the Codex sandbox. Keep `adversarial` empty because the only supported native Windows provider is Codex. Native Windows fixes preserve existing Git executable modes, including case-only renames, but cannot create or change executable modes or preserve them across other renames; use Linux or macOS for those fixes. Place `config.local.json` and provider logins outside source snapshots. The operator manages the service account and work-root ACL; Minion validates paths but does not audit host directory permissions. Windows file ACLs, rather than Unix `chmod`, protect these paths.

Run `-check` while the persistent service is stopped; it takes the state lock. If the service uses environment-based credentials, provide the same protected environment to this check.

When upgrading a local checkout from a version with host process supervision, remove `command_max_tasks`, `command_max_memory_mib`, `work_root_max_bytes`, and `claude.allow_all_unix_sockets` from `config.local.json`; these settings no longer exist and unknown configuration fields are rejected. An old `state.json` containing `unconfirmed_process_job` also cannot be opened. Stop the old service and confirm its worker has exited before removing that obsolete field from the state file. Complete or manually reconcile any pending `job_failures` under the old version before upgrading: those records do not say whether a model call began.

Normal startup and `-check` verify Git's minimum version and run a bounded private synthetic offline bundle/import/index round trip under `work_root`, before AI or GitHub preflight. The check uses Minion's production Git paths with synthetic local files; it reads no project repository, fetches nothing and runs no model. A failed version or capability check stops startup with its cause. This proves the installed host Git operations exercised by the check, not every repository's compatibility, future executable immutability, account/API availability or Git execution inside an AI sandbox. Operators still provision tools and pinned skills. Recovery of a previously assigned or terminal accepted action can run before new-work preflight, using GitHub and any needed local Git or audit tools without starting a worker; new work still requires the normal checks. Install-only, usage and locked one-pass shortcuts do not gain this Git requirement.

The default `-mode=in-process` runs actions in the service process. With no `-loop`, Minion makes one cron-friendly polling pass; add `-loop` for a persistent service. On Linux, macOS and Windows, `-mode=orchestrate` starts one selected local executor child and uses the same one-pass or `-loop` polling behavior:

```sh
./bin/minion -config ./config.local.json -mode=orchestrate -loop
```

`-check` and `-install-skills` remain setup commands and do not start an executor. `minion usage` remains a separate reporting command; see [Usage reports](#usage-reports). `-mode=execute` is the internal child entry point: it reads trusted selected startup data from standard input and cannot be combined with `-config`, `-loop`, `-check`, or `-install-skills`. Do not launch it manually.

For scheduled one-pass runs, save this as an executable `/path/to/minion/run-once.sh`, adjusting the checkout and CLI paths:

```sh
#!/bin/sh
set -eu
export PATH=/usr/local/bin:/usr/bin:/bin
cd /path/to/minion
exec ./bin/minion -config ./config.local.json
```

Add `*/5 * * * * /path/to/minion/run-once.sh` to that user's crontab; use the same credential environment as the persistent service.

The `gh` token needs access to [GitHub notifications](https://docs.github.com/en/rest/activity/notifications?apiVersion=2022-11-28) and the whitelisted repositories. GitHub's notifications endpoint requires a classic personal access token or OAuth token; fine-grained tokens and GitHub App tokens do not work there. The bot needs repository **write** access so it can query [collaborator permission](https://docs.github.com/en/rest/collaborators/collaborators?apiVersion=2022-11-28) and push fix branches to its fork. Fixes also need access to the base repository's private fork PR policy and the fork's Actions settings; an unreadable policy causes refusal. GitHub requires the classic token's `repo` scope for those settings; its fine-grained equivalent is repository Administration (read), though fine-grained tokens cannot poll notifications. When push rulesets exist, the token needs ruleset write access for GitHub to include their bypass lists. `-check` verifies notification and repository access, including fork and push-rule safety when `fix` is enabled. GitHub credentials are read from `GH_TOKEN`/`GITHUB_TOKEN` or `gh auth token`. AI provider API keys can be set in `codex.api_key` and `claude.api_key` in the ignored `config.local.json`; see authentication below. Keep real keys out of the checked-in sample and set `chmod 600 config.local.json`.

Edit `config.local.json` to change the repositories monitored for commands or their enabled actions. Each `repositories` entry needs an `owner/repo` name and its GitHub `id` and `owner_id`. `actions` lists the command names allowed in that repository, drawn from the top-level `commands` mapping. `allowed_actors` can restrict commands to named committers in addition to the GitHub permission check; each listed login also needs its numeric ID in `allowed_actor_ids`. `invitation_owners` lists accounts whose current and future repositories may invite the bot; each listed login needs its numeric ID in `invitation_owner_ids`. Invitations with `write`, `maintain`, or `admin` access automatically add the repository and its IDs to `config.local.json` with the configured command names. A command with a missing required skill stays unavailable until it is installed. The default in-process mode starts monitoring an invited repository in the same poll. `-mode=orchestrate` waits for a restart and a new worker selection, preserving the repository's original notification cursor meanwhile. Existing repository actions and actor restrictions are preserved. `start_at` may be set to an RFC3339 timestamp before the state file is first created to process older notifications. Opening state saves that cursor even if later startup checks fail. Without it, a new state file starts at the current time.

When a configured command uses the `fix` action, a repository added from an invitation enables it. Provision its bot-owned fork with Actions disabled before fixes can publish; `-check` reports a missing or unsafe fork.

Confirm that each repository and account is still the one you intended to trust, then look up its immutable GitHub ID with authenticated `gh` commands, for example:

```sh
gh api repos/OWNER/REPO --jq '{id, owner_id: .owner.id}'
gh api users/OWNER --jq .id
gh api users/ACTOR --jq .id
```

Copy those values into `id`, `owner_id`, `invitation_owner_ids`, and `allowed_actor_ids` as applicable. The sample `config.json` contains placeholder IDs. A missing, extra, or nonpositive pin stops startup; Minion does not infer trust from a login that another account may have claimed. Pending retries without IDs cannot run; they are discarded when their notification is seen or their retry becomes due.

The top-level `commands` object maps each command name to an application `action` and one or more skill sources in `skills`. Supported actions are `review`, `fix`, `comment`, and `security-audit`. The application action, not the skill, determines whether Minion posts a review or thread comment, pushes a fix branch, or writes a validated security report. Omit `commands` or set it to `null` to use the four mappings in [config.json](config.json); set it to `{}` to disable all commands. Every repository's `actions` list must name configured commands. A mapped command runs only when all its required skills are available to the main provider: downloaded skills need matching Minion install metadata, while the embedded `builtin://anti-prompt-injection` skill needs no installation. Custom GitHub sources use `https://github.com/OWNER/REPO/tree/REF/skills/NAME`. `REF` is a single path segment; the path after `skills/` may contain nested components, with its final component used as the installed skill name. The embedded URI is the only supported `builtin://` source.

The `always_on_skills` list selects optional skills for every run. Omit it or set it to `null` for the default embedded anti-prompt-injection skill and caveman GitHub skill, in that order; set it to `[]` to use none. An external always-on skill is used when installed and skipped otherwise. The main model receives its command skills and installed always-on skills. The critic receives only installed always-on skills, so a command skill cannot turn its read-only critique into another execution of the task.

`-install-skills` copies configured embedded skills and downloads configured GitHub skills into `$HOME/.agents/skills/` for Codex and `$HOME/.claude/skills/` for Claude, then exits. The embedded anti-prompt-injection skill works in Minion jobs without this switch; copying it also makes it available to interactive Codex and Claude. The installer resolves each GitHub ref to its current commit, installs its complete skill directory, and records the fetched source and commit. The default `main` URLs therefore get their latest versions each time. GitHub skill repositories must be publicly readable because the installer fetches them without credentials. It replaces existing same-name skill directories in both locations, including manually installed copies; keep local customizations under other names. Run it explicitly when adding or updating skills; ordinary Minion runs never download them. Review each external source and fetched commit: skill instructions guide the models, and Minion runs the security-audit skill's validator scripts under the service account.

Stop Minion before editing its configuration. Install skills and run `-check` after editing it.

### Main model and adversarial critic

`main` selects `"codex"` (the default) or `"claude"`. `adversarial` is optional; omit it or use `""` to disable the critic. When enabled, it must select the other CLI. The `codex` object accepts `model`, `reasoning_effort`, and `api_key`; `claude` accepts `model`, `effort`, and `api_key`. Omitted model settings use the provider's defaults. For example:

```json
{
  "main": "codex",
  "adversarial": "claude",
  "critic_stopping": {
    "max_rounds": 5,
    "nonblocking_after_round": null,
    "consecutive_no_blocker_rounds": null
  },
  "codex": {
    "api_key": ""
  },
  "claude": {
    "api_key": ""
  }
}
```

Add these fields to the service config. Swap the two provider names to use Claude as main and Codex as critic. Install both selected CLIs, configure API keys or authenticate them interactively, then run `-check`; an unused CLI is not required.

A nonempty `api_key` takes precedence over environment credentials and saved CLI login for startup validation and job execution. Use an [OpenAI API key](https://learn.chatgpt.com/docs/auth#sign-in-with-an-api-key) for Codex and an [Anthropic API key](https://code.claude.com/docs/en/authentication#authentication-precedence) for Claude. With keys empty or omitted, Codex uses `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN` or saved login; Claude uses its saved login. Configured keys are not placed in prompts or command arguments, and do not replace the operator's saved login. Minion preserves them when automatically registering a repository in the deployment config. The service requires a resolvable native user home for CLI authentication and session files.

In selected local-worker mode, the worker uses a transient copy of selected credentials for startup preflight, drops those references before its first pull, and receives credentials separately with each private assignment. It drops each job's references and closes CLI sessions before uploading the result or pulling another job. Saved CLI login remains with the worker's service account; Minion does not copy authentication directories. Operators control network egress outside Minion. Clearing Go references and temporary files does not guarantee erasure from process memory.

Claude support requires an installed CLI that passes authentication, model-catalogue and fresh/resume invocation probes using the requested sandbox and tool options; Minion imposes no Claude release-number minimum. Claude's Linux sandbox uses `bubblewrap` and `socat`; the CLI checks whether it can start. macOS uses Claude's native shell sandbox. Its restricted execution tool set contains only Bash; the `security-audit` action is disabled with Claude as main because that workflow requires independent subagents. `review`, `fix`, and `comment` (default `audit` command) actions support either main provider on Linux or macOS.

Claude runs in [safe mode](https://code.claude.com/docs/en/cli-reference) with automatic instruction discovery, hooks, plugins, MCP, and connected tools disabled. Each action keeps stable source, context, report and role-runtime paths until completion. Main revisions resume their existing native conversation; scoped finding verification resumes the latest critic conversation. Each full review starts a new independent conversation at the same paths, after clearing that role's writable scratch. Role sessions never cross actions or share main/critic history. Every invocation reapplies its selected schema and CLI tool policy; conversation reuse does not add automatic quota retries or service-restart recovery. Claude stored-login transcripts follow normal CLI retention. Preexisting and unverified rollouts and saved login files remain. Role cleanup retries once; persistent failures report generic `cleanup_failed` and put the recovery path in a private `cleanup_recovery` diagnostic. They can leave rollouts, runtime files or materialized-skill directories for operator removal. An ongoing conversation retains its natural history. The explicit cross-round refutation list below contains only refutations; its durable ledger also stores call receipts and verdict flags, without answer or critic-feedback text. Earlier findings or approvals are not precedent preventing changed code from being examined again.

With a critic configured, the main model returns a public `answer` and private `refutations`. The first critic reviews the complete candidate against the original task and baseline. After a revision, scoped verification checks earlier findings against the changed files and private counterevidence; a valid no-blocker verification triggers a separate fresh full review. The final permitted proposal also receives that full review after completed blocking verification, without discarding its blockers. Verification alone never permits publication or counts toward the no-blocker streak. Full reviews receive no previous findings, answers or refutations. Normal publication requires a fresh full review that meets either the approval condition or the configured nonblocking stopping condition, with required verification findings still subject to the stopping policy. At the hard round limit, a completed full review may instead permit caveated publication as described below. The next revision retains rejected feedback from both phases. The main model must implement valid findings at every severity, including nits and simplifications, or supply concrete counterevidence or a task constraint. These are model instructions, not mechanically verified guarantees.

The cross-round refutation list appends only revised main proposals' `refutations` field (round 2 onward), with its original round and private text after NUL removal and configured-key redaction, rather than answer or critic-feedback text. The first proposal must leave refutations empty; preemptive first-round text is discarded. The model is instructed to exclude implemented-finding summaries and approvals from refutations. Each revision and scoped verification also receives the immediately previous answer and critic feedback. They reuse applicable counterevidence; changed code, changed task constraints or material new evidence can invalidate an earlier refutation. Changed code remains open to review. Main-model refutations are claims, not inferred critic acceptance.

With a critic configured, the service atomically checkpoints call receipts (including verdict flags) and the refutation list under `work_root/reviews/<attempt-id>.json` before another call or publication, including failed actions. Review checkpoints and final Results remain executor claims: the parent validates identity, structure, the call prefix and decision consistency, but cannot prove what a critic saw. An initial metadata checkpoint verifies storage after work-root admission. Minion creates the record with mode `0600` and its directory with mode `0700` on Unix; the operator controls inherited host ACLs on Windows. A stable action-scoped refutation file is refreshed between calls, supplied to revisions and scoped verification, and removed when the action ends. The journal logs call phases, verdict and stop facts, input/cached-input/output token counters and accounting completeness, plus identity, location and refutation count, without private text. Retention failure stops model work and publication; identical final evidence does not rewrite the checkpoint. Records do not mean publication succeeded or resume interrupted actions. Complete discussion logging remains separate [#98](https://github.com/linkdata/minion/issues/98)/[#99](https://github.com/linkdata/minion/issues/99) work.

Fix critics inspect a frozen candidate; Minion asks the selected CLI to keep the supplied source read-only during actions that share it. Audit critics inspect frozen reports with configured API keys redacted. Verification and full review of one proposal share immutable inputs and the original baseline, not the previous candidate tree. Minion rejects changes to the copied fix candidate and audit report files and their regular/executable modes and exports the frozen bytes; later live workspace changes cannot alter that export. Empty directories and directory modes carry no transferred source state and are not attested. Before result export, audit metadata is projected to supported fields: portable target/companion paths and ownership entries for known artifacts; unknown extensions are dropped. The parent validates uploaded metadata again; extra fields do not select its filesystem or GitHub targets. Raw audit artifact content is changed only by NUL removal and configured API-key redaction before critic review and export; JSON artifacts may be re-encoded when decoded values or keys change. Prompts request repository-relative paths, but a model can still quote executor-local paths; Minion does not mechanically remove them. Missing artifacts and empty non-JSON companion files can receive feedback. An empty `REPORT.md`, invalid or ambiguous JSON, or any audit artifact still exposing a configured key stops before review; unsafe, unreadable or oversized inputs do too. Model agreement does not replace validation or publication controls.

Fix changes containing either configured provider key as literal text, a JSON string or a single-pass HTML entity stop before critic review or publication. With a critic configured, proposed answers, private refutations and critic feedback containing a key in those forms stop before crossing to the other model. A separate accidental-copy guard rejects an exact whole-refutation reply of any length, or complete-sentence copies of at least 24 Unicode characters in public replies or newly disclosed Fix content, after case, space, Unicode, HTML-entity and surrounding `*`, `_` or backtick normalization. It also checks raw audit finding titles and fingerprints before quoting them in the public summary. Exact short matches are limited to whole replies and audit titles; a fingerprint or Fix file can legitimately contain the same generic short value as a refutation. A quote already present in the parent-held head or base source, or in the parent-prepared GitHub title, description or requester notes, does not block a public reply or unrelated edit. Its public copy search and source-quote search each have a cumulative 1 GiB work budget; publication is refused when either search cannot finish. Already proven source quotations remain allowed. Exact whole-reply/title and configured-provider-key checks remain in force. Private audit artifacts are outside this public-output guard. Short partial copies, paraphrases, nested escapes and discussion omitted by a hostile executor remain outside it. The provider-key check does not recognize arbitrary encodings such as base64.

The `critic_stopping` object groups the stopping policy. `max_rounds` counts main proposals, including revisions: default 5 when omitted or 0; bounds are listed under [Action boundary](#action-boundary). N rounds allow at most 3N−1 main/critic calls. `nonblocking_after_round` controls the absolute-round threshold. Omitted or `null` defaults to maximum minus one (4 by default; 0 for a one-round maximum, 1 for a two-round maximum). Explicit 0 requires every finding cleared for normal acceptance; it does not disable caveated publication at the hard limit; Minion development deployments use this strict setting. The old top-level `critic_max_rounds` and `critic_nonblocking_rounds` keys are rejected, including when combined with the nested settings.

`consecutive_no_blocker_rounds` defaults to 2 when omitted or `null`. At or after a positive absolute threshold, nonblocking acceptance also requires this many consecutive proposal rounds whose fresh full reviews explicitly report no blockers. Explicit 0 disables only the streak requirement. A value above `max_rounds` prevents acceptance through the streak before the cap. A full review with blockers resets the streak; verification, missing, contradictory, incomplete or failed verdicts never count. Fresh full approval permits immediate publication once required verification findings are cleared. In strict mode, a new full approval cannot discard unresolved verification nits. Otherwise, remaining nonblocking findings can be accepted only when both threshold and streak conditions hold. At the hard limit, a completed, valid fresh full review can instead stop with `round_cap`, preserving any final verification blockers even if the full review approves. This outcome does not satisfy normal acceptance.

At `round_cap`, the public result states the original maximum, that normal critic acceptance was not reached, the reported full-critic approval and when a final-candidate review phase reported blockers. This application-generated caveat precedes the worker-supplied body or the parent-rendered audit summary; it never includes private critic discussion or refutations. Audit artifacts retain their original validated bytes. Oversized projected output is refused without truncation. Missing, invalid, incomplete or failed reviews, deadlines, authorization failures and source, artifact and publication checks still stop the action. A capped fix with changes is pushed for human review and is never automatically merged. Publication success, critic approval and review completion remain distinct.

Blockers are concrete correctness, security or task failures; stylistic nits and simplifications without that impact are nonblocking. Until the configured nonblocking stopping conditions are met, normal publication requires explicit approval with every finding implemented or evidence-refuted. Every review round is instructed to investigate its whole assigned scope comprehensively, collect findings at all severities in one pass, await delegated work and checks, and make a final coverage pass. Finding a few issues or no blockers is not a stopping point. Reviews must disclose unchecked scope and any runtime, context, quota or dependency limit that prevents completion. A critic is instructed to classify unfinished assigned review scope as blocking. The critic must explicitly attest `review_complete` for its assigned phase. A valid incomplete verdict reports blockers and retains its call evidence, then terminates the action without a revision, streak increment or publication. Missing or contradictory coverage evidence is invalid. This is a model attestation, not mechanical proof of inspected files or delegated work; native CLI completion and awaited-helper checks remain prerequisites.

The executor-reported critic approval and blocker flags stay separate from the application's stopping decision. Per-call `review_complete` describes assigned review coverage independently of `complete`, which describes token-accounting coverage. A completed review can have incomplete usage accounting; complete accounting cannot make an unfinished review publishable. Per-call `has_blockers`/`no_blockers` evidence distinguishes blocking and nonblocking verdicts from an invalid verdict or provider failure (both false). Failures after a native call, such as snapshot verification or usage persistence, retain its parsed verdict. Journal `policy_allows_full` and `no_blocker_verdict_streak` replay eligibility and the streak from reported verdicts; neither proves that integrity checks passed or execution advanced. `policy_met` is true only for an actual normal acceptance decision (`approved` or `nonblocking`) after call integrity checks. Journal `stop_reason` exposes the separately recorded `critic_stop_reason`; `round_cap` sets `capped=true` with the original `critic_max_rounds` and final-candidate `cap_has_blockers`, while `policy_met` remains false. Without an actual decision the reason is empty. Fix reply attempts also log the saved cap facts when recovering publication. Retained verdict flags can show approval even when integrity checks aborted that call before acceptance. The private review record retains the actual decision separately from those flags. A recorded stopping decision does not prove publication succeeded. See the [failure policy](#failure-policy) for exhausted budgets.

`max_runtime_minutes` defaults to 240 (allowed 1–1440) and caps the original execution, including result acceptance and publication retries, from the first action acceptance time. An entered durable receipt write may finish syncing after the deadline, but that result cannot authorize publication after expiry. Executors receive the remaining duration at dispatch and account for transfer time using their own elapsed clock, without comparing host wall clocks. `inactivity_timeout_minutes` defaults to 10 (allowed 1–240). The config accepts it now; #128 will enforce it from real executor progress. Once enforced, a silent model or tool turn may reach the default 10-minute inactivity limit even while it is working. Neither limit can be disabled; 0 or omission selects its default. Before upgrading an existing config, rename `job_timeout_minutes` to `max_runtime_minutes`; the old key stops startup. An inactivity limit at least as large as max runtime is allowed but ineffective. The first accepted time and deadline are saved with failed-job state and reused across retries; selected worker mode also saves the request and reservation before reaction and restores an unassigned attempt after process restart. Releasing an unused reservation does not renew the job deadline. The first terminal decision is persisted and survives restart; late results cannot replace it. Admission, cleanup and fixed refusal/failure-reply budgets can run outside the action runtime. The reaction is outside it in in-process mode; selected mode saves acceptance and starts the deadline before reacting. In-process mode pauses notification polling and invitation checks during a new job. Startup replay of a saved result still services due invitation checks and existing terminal failure replies. Selected-worker mode pauses new notification polling while continuing those checks and replies.

With a critic, both CLIs receive schemas for main proposals and critic verdicts; Minion validates their contents. Decoded main answer/refutations share 58 KiB, raw proposal JSON allows 6×58 KiB+128 bytes for escaping, and critic JSON allows 64 KiB. NULs are stripped from main answers; with a critic, every proposal must contain a nonblank answer. A changed fix can discard an oversized unused summary after review, or a blank summary without a critic. A no-change fix needs a publishable answer before critic review. Audit publication uses a parent-rendered summary of validated structured records; the worker answer is ignored, while `REPORT.md` is validated and retained privately with a raw 58 KiB limit. Audit metadata such as `run_status`, `execution_policy` and `shared_file_owners` consists of executor declarations checked for consistency, not independent proof of completion, isolation or authorship. Without a critic, the main model keeps its ordinary response format. Every task states the rendered publication budget. Oversized published output is refused.

Codex uses a private temporary project root per action/role beside the supplied source snapshot and reads source through its absolute path. Source `AGENTS.md` files are not loaded as project instructions, and source `.agents/skills` are not offered as skills. The automatic skills catalogue is hidden; only skills selected by Minion's config are named in its prompt. The source includes a sanitized local `.git` directory with complete object history. Minion verifies the supplied Git metadata after model calls and refuses unexpected changes. Startup checks instruction and skill discovery with inert files using the installed Codex CLI, without an inference turn, and stops if those files enter an isolated job prompt. Repository source text remains untrusted context that can influence model output; inspect generated fixes and reports before relying on them.

When Codex is selected for either role, orchestrator startup or `-check` verifies its instruction boundary, queries the installed Codex CLI's [model catalogue](https://learn.chatgpt.com/docs/app-server#models), and validates the model and its supported reasoning efforts. A startup recovering an already accepted action may finish that recovery first; it runs these checks before continuing into new work. Omitted values are resolved from that catalogue and pinned for the life of the service. Invalid model settings, an incompatible Codex protocol, a failed instruction check, or a failed catalogue lookup stop new notification polling. A first start may already have created the state file and saved its cursor (see `start_at` above). The log includes the rejected value and supported choices when available. Missing required skills disable their mapped commands; missing always-on skills are skipped. Model discovery has a 30-second timeout and does not start an inference turn. The systemd service retries failed startups every 30 seconds, so a removed model or effort requires correcting `config.local.json` or the Codex installation before work resumes. Restart Minion after upgrading Codex or installing skills to revalidate. Catalogue validation checks compatibility, not future API availability or account quota.

Minion waits for its direct external commands, including the AI CLIs, Git and audit validators. On cancellation it interrupts the direct command and bounds the wait. AI CLIs own cleanup of their model-tool processes. Minion does not inspect or stop descendant processes. An interrupted complete-report write can leave a `work_root/audits/.complete-*` staging directory with private report bytes; the next retry removes its own stale stage, and an operator can remove old stages after the action stops. A failed validation-scratch cleanup can leave `work_root/.minion-audit-validation-*`. Worker diagnostic records contain private executor text. To stop a stuck publication replay after inspection, stop the service, back up the state file and sidecar, remove `state_path.result`, then restart. Invitation checks become due every 15 minutes. Selected-worker mode checks them during idle waits and active actions; in-process mode checks when the monitor regains control. ## Action boundary

The AI CLIs enforce model-command sandboxing. Minion requests Codex's native read-only or workspace-write mode and Claude's native Bash sandbox, validates supplied inputs and returned results, and controls action lifecycle. The orchestrator prepares source and controls GitHub writes. The local `Runner` consumes a bounded, credential-free `Job` and returns changes, reports, usage and diagnostics in `Result`.

The orchestrator now calls the typed `Executor` interface, with synchronous identity/source-bound checkpoints before each paid call, after returned usage (including failed or canceled calls), and for review prefixes and the separate stopping decision. Missing or failed acknowledgements prevent continuation or publication; a final Result cannot replace them. The same Runner pipeline serves this interface and direct local `Run`; optional usage still skips only accounting, while critic orchestration requires private evidence.

Protocol version 11 adds a required assignment stop-grace field and a required remaining-time field for canceled/deadline replies, so older HTTP peers fail the pull before assignment. Version 10 added per-assignment AI credentials outside the portable Job. It also carries relative remaining runtime budgets, critic stopping settings, explicit per-call review coverage and capped publication decisions, without process-scope failure fields. The versioned `Status` contract binds worker observations to the accepted job and source, with separate message, progress and log sequences plus phase, round, review phase and worker state. `Sequence` advances for each status message; `ProgressSequence` advances only for observed execution progress, and `ProgressAge` is elapsed time since that progress (or attempt start before any). Heartbeats and logs do not reset progress age; `LogSequence` advances for captured log entries. The parent accepts gaps in the observation sequence, but rejects replayed or regressing counters, phases and worker states, including observations arriving after the outcome. Main, critic and upload phase reports require matching parent-accepted callback facts; prepare and cleanup can be reported without a callback. A cleanup label is an untrusted observation, not proof of worker release or capacity. Progress age cannot exceed elapsed parent time. `HTTPExecutor` and `RunHTTP` can carry one Job, synchronous checkpoints, finite typed failures and a partial or complete Result over standard HTTP. The parent owns the handler; the worker initiates one pull and executes the existing Runner pipeline. Full identity/source binding and increasing request sequences reject foreign or repeated inputs. A disconnected pull can retry before assignment bytes are sent; a delivered assignment is never redispatched. There is no pending-assignment queue. The default service still executes in-process. The selected local worker mode starts and joins one direct child on Linux, macOS and Windows. Configured remote worker authentication remains [#123](https://github.com/linkdata/minion/issues/123) work.

The internal `RunHTTPLoop` lets a selected worker pull another Job only after a valid final outcome ACK, including after a failed Job. It exits cleanly when canceled before a pull or after an acknowledged idle shutdown. Uncertain delivery and failed required control exchanges stop the loop with an error; optional status observation failures are logged. The `-mode=orchestrate` switch selects this local worker path.

`ListenLocalExecution` serves that handler over HTTPS on an ephemeral IPv4 loopback port. Each direct worker receives its own server certificate and client token through bounded startup stdin, outside arguments and the environment. `NewLocalExecutionClient` trusts only that certificate, dials the fixed loopback address without a proxy, refuses other origins and redirects, and sends the token only after TLS succeeds. The endpoint checks the token before decoding any protocol body. A local process without those credentials cannot authenticate as the worker or impersonate the parent; another process can still interrupt service. On shutdown the parent drains accepted callbacks while HTTPS remains available, lets the direct child receive idle shutdown until it exits or the stop deadline arrives, then closes HTTPS and joins the child. The first HTTP stop deadline is reused for direct-child termination and HTTPS shutdown; capacity stays retired while the child or accepted callbacks remain unresolved. No socket path or runtime directory is created.

HTTP bodies require uncompressed JSON, one value, known fields and valid UTF-8. Encoded caps are 256 MiB for the assignment, 64 MiB for the outcome, 8 MiB for review and 128 KiB for control/ACK bodies. The assignment credential bundle has an 8 KiB aggregate raw-byte cap and is excluded from Job, Status and Result. A conservative assignment estimate counts worst-case escaped text and credentials, per-file base64 padding and envelopes before encoding; it can refuse an otherwise valid decoded Job. Before typed decoding, 200,000 total JSON tokens and nesting depth 64 bound container expansion; maximum canonical Job arrays fit that token budget. Field limits preserve raw failed usage receipts without accepting them as a valid complete Result.

The bounds allow six encoded bytes per UTF-8 text byte and `4 * ceil(n/3)` base64 bytes for each separate byte slice, plus object keys, scalars and envelopes:

| Body | Conservative size basis |
| --- | --- |
| Control/ACK, 128 KiB | Pinned identity and small checkpoint/status metadata; the largest finite failure adds an 8 KiB diagnostic, still within the control body cap after text escaping and metadata. |
| Review, 8 MiB | At most 19 refutations of 58 KiB each expand to about 6.46 MiB, plus 59 calls with bounded 128-byte metadata fields, identity and envelope. |
| Outcome, 64 MiB | The finite raw shape permits seven 5 MiB artifacts, about 46.67 MiB in base64, plus 1 MiB aggregate changes, about 1.34 MiB in base64. Escaped refutations, call metadata, a 58 KiB answer, 100 bounded diagnostics, change/artifact paths and failure/envelope overhead keep the combined bound below 63 MiB. This uses all seven artifact maxima even though a valid complete `REPORT.md` has a smaller 58 KiB raw limit. |
| Assignment, 256 MiB | Deliberately narrower than decoded Job validity: separate 64 MiB bundle and file-content budgets, a 1 MiB diff, 64 MiB task text, role/skill settings and four path lists can exceed a GiB after encoding. The pre-encoding estimate counts actual admitted lengths with worst-case expansion, individual base64 padding, container overhead and an assignment reserve, then rejects estimates above 256 MiB. Even a 64 MiB ASCII description can be conservatively refused although its actual encoding would fit. |

The accepted hard expiry includes result validation, encoding, waiting and transfer. Publishing-host audit validators run during publication from the saved result, outside the outcome ACK path. Parent call admission and outcome sealing check the deadline directly, without waiting for its cancellation callback. Assignment pulls may wait for work without a transport deadline; once headers arrive, reading their response body is limited to 30 seconds. Positive replies require HTTP 200. A held cancellation watch is admitted before execution. The caller supplies one bounded stop budget (30 seconds by default). The parent starts it once on cancellation, expiry, shutdown, or required control failure; the worker starts it on its own expiry, cancellation, or Runner completion. Serial control requests share the worker deadline while returning available paid receipts. The same budget accompanies the assignment, and an earlier parent stop sends its remaining time to narrow worker control. A delayed watch reply can leave the worker's relative timer later than the parent deadline; the parent rejects late controls and outcomes. Admitted transaction network reads and writes contract to the stop deadline; pre-admission `/next` and `/cancel` bodies retain 30-second request limits. Accepted context-free saves and bounded JSON encoding/validation may finish after grace; the parent fences late outcomes before publication. A stalled filesystem save can keep Execute waiting past grace. A parent-observed failure to deliver an assignment or required checkpoint ACK blocks publication and quarantines capacity even if a later bound outcome arrives. A bound received outcome survives loss of its receipt ACK; a detected receipt-ACK write failure quarantines capacity. A successful final receipt ACK can resolve independent malformed-watch transport uncertainty during final upload. It does not clear Runner or required-checkpoint failures, actual parent cancellation/deadline, parsed parent replies or external caller causes. Known pre-model request transport failures observed by the parent retain infrastructure retry classification. Worker-reported transport or output-limit failures do not establish that classification; a bound failed outcome without parent-proved uncertainty consumes an attempt. An unknown execution outcome consumes the attempt and is never automatically repeated, including after cancellation or network failure. Receipt ACKs do not replace checkpoint saves or authorize publication. HTTP completion does not prove direct worker exit; the caller waits for that process separately. Call Close while the server still serves control requests. Supplied clients must permit a held watch and concurrent control requests; their configured timeout is preserved and redirects are refused.

The HTTP client currently emits actual `prepare` and `upload` observations. The optional upload Status gets at most half of the worker's stop grace so the final Result can still be attempted. Periodic/durable Status and recoverable final upload remain [#125](https://github.com/linkdata/minion/issues/125)/[#135](https://github.com/linkdata/minion/issues/135) work; discussion/log payloads and their durable acknowledgements remain [#98](https://github.com/linkdata/minion/issues/98)/[#99](https://github.com/linkdata/minion/issues/99) work. A Status does not authorize publication or prove worker cleanup.

PR context always contains changed paths and merge-base versions of changed/deleted files, alongside pinned head source and separate base-tip identity. Complete Git history includes the base tip; supplied comparison file excerpts use the merge base. Diffs ignore repository attributes; an oversized diff alone is omitted and marked incomplete. Complete-tree limits include omitted links and apply to the entire merge base, even when only selected files transfer; shrinking an over-limit or unsupported base does not bypass them. Preparation uses ordinary complete clones and fetches, without shallow history, partial objects, filters or lazy fetching. Clone/fetch has no object/byte cap beyond the action deadline. Shallow/incomplete sources and oversized bundles are refused; Minion never substitutes truncated history.

Symlinks/gitlinks are omitted and declared in `source.json`; its single `omitted_scope` applies to the whole snapshot (`head` for issues or `head_and_base` for pull requests). `head_omitted` separately identifies current link paths for audit coverage; links cannot provide line citations. A base-only omission may have regular descendants in head. Fixes cannot modify omissions/descendants or replace their ancestor directories with files. Exact Git spelling is preserved, including case and backslashes; unrepresentable source is refused. Git source admission rejects NTFS/HFS aliases of `.git`. Fixes additionally require backslash-free regular paths and a final layout without Unicode SimpleFold collisions, including omissions. Security audits reject current regular and omitted-link paths that the installed report validators cannot cite before model work; base-only paths are comparison context. Components allow 255 UTF-8 bytes and relative paths fewer than 4096 bytes; native Windows rejects paths that cannot be safely represented there. Host filesystem and absolute-root limits still apply, so executor acceptance does not guarantee trusted import or cross-host compatibility.

Models see tracked `.gitignore` files and complete local history. The supplied repository is rebuilt from objects and refs, without copying source config, hooks, alternates or credentials. Implicit bare-repository discovery is refused; trusted operations that need a bare repository name its Git directory explicitly. Minion verifies supplied Git metadata after calls; fix critics receive an independent copy of the original repository alongside the candidate files. Omitted head links are marked skip-worktree so their absence does not appear as a deletion. A private offline index outside the supplied source snapshot collects fixes without remotes, credentials, hooks, filters or source Git config. Tracked edits count; ignored new build outputs do not. A case-only rename to an ignored spelling is refused instead of exported as a deletion. Case-insensitive `.git` components stay excluded. Wholly untracked nested repositories must be removed or ignored. Traversed ignore/attributes controls must be regular files; an ignored untracked `.gitignore` is refused if Git loads it but would not export it. Unused controls in ignored directories with tracked files are allowed. Skipped ignored subtrees consume no control-file scan entries beyond their visited parent; case-spelling checks may still read names beside tracked files. Case-spelling checks have a cumulative 100,000-entry scan limit; a larger ignored cache beside a tracked file may cause the fix to be refused. Orchestration rechecks the fork and validates imported data before its commit/push; executor Git metadata never transfers.

Codex uses its native read-only mode when no output directory is needed. Fixes use workspace-write for source edits; audit reports use workspace-write for their separate report directory, leaving the source outside writable roots. Minion supplies source, context and selected skill paths, disables unselected integrations, and checks `exec` and `exec resume` options, runtime config keys, the model catalogue and instruction isolation without requiring a Codex release number. The CLI selects and enforces its sandbox backend; Minion does not verify host-level read isolation. Select an instruction-free `CODEX_HOME` and authenticate there; Minion refuses homes containing global `AGENTS.md` or `AGENTS.override.md`. Every Codex model call disables cross-session memories. Explicit native provider-directory overrides are resolved and pinned for each action role; a mid-action change is refused. Codex uses that directory for rollout recovery. Codex calls require a resolvable native user home or `CODEX_HOME`; rollout accounting and helper verification read that directory.

Native completion is separate from accounting. An oversized provider event cannot be recovered by a later answer. Known Codex helpers require proof that their latest own turn completed. In measured Codex 0.160.0 runs, resuming the role conversation did not restore its prior helper roster; earlier helper reports remain in the conversation. On resume, a wait/close-only reference to an unchanged, already completed helper needs no new turn. If close appends records, the changed log follows the ordinary attribution and completion checks. Sending input, spawning, unfinished baselines and changed logs retain the completion checks; intentional close/interrupt of active work, missing or unreadable logs, inherited-only entries and capped tails that prevent proof reject completion. A completed attributable helper lifecycle with missing counters only leaves usage incomplete. On resume, discovered or previously known owned helper rollouts without current activity require an exact unchanged byte baseline; new, changed, ambiguous or unverifiable logs reject completion. A missing or changed known identity keeps later resumes of that role session rejected until its evidence is restored or a new conversation starts. Baseline-entry, per-rollout byte and separate 512 MiB proof limits also constrain this proof. Broader header/entry discovery caps and unreadable unrelated directories leave usage incomplete. Unusable historical content alone does not invalidate a fully read byte baseline. Minion waits for the direct CLI process; the CLI owns its model-tool processes. The two-second pipe-drain bound still rejects a call whose inherited output pipes stay open after the CLI exits.

Claude checks bounded stderr for wait-ceiling stops while retaining its last 8 KiB; managed settings may override the launch environment. Non-ambient stopped tasks require a fresh root response and result, and a result with a non-`completed` terminal reason cannot complete a call; a later completed result may. An unusable quota rejection or permanent native memory-pressure stop gets one non-renewable second to flush counters/result before cancellation; an earlier action deadline still wins. Later allowed events cannot erase interrupted work; usable overage and near-limit warnings do not fail a successful call. Reset times are informational.

The journal records role, round, phase, model settings, accounting completeness, diagnostic counts and private attempt-record paths. Worker diagnostic codes and messages stay in those private records. `MINION_LIVE_CODEX_BOUNDARY=1 go test ./internal/codexcli -run '^TestInstalledCodexInstructionBoundary$' -count=1` opts into an installed-Codex check that renders local inert prompts without inference and skips if the CLI is absent.

Create the ignored `live-tests.local.json` in the repository root to enable the GitHub live tests. Without it, they skip:

```json
{
  "owner_login": "example-owner",
  "bot_login": "example-bot",
  "repository_url": "https://github.com/example-owner/example-repo"
}
```

Replace the sample values with two accounts authenticated in `gh` and a repository owned by `owner_login` that both can read. `issue_number` selects an owner-authored issue with an owner comment; `pull_request_number` selects an open owner-authored draft pull request with an owner comment. Each fixture owner comment must have an update time more than one second after thread creation. These numbers are optional for basic read-only checks. The write lifecycle and fix action need `issue_number`; live reviews need `pull_request_number`; the security-audit action needs both. The `linkdata/miniontesting` pull request fixture also needs a bot-authored inline review comment and submitted review with a non-empty body. Optional `bot_ssh_key` is an absolute path to the bot's SSH private key or a path relative to the repository root; it enables SSH identity and repository read checks. SSH checks also require a trusted github.com host key already present in the default SSH known-host files. Put no token or key contents in this file.

Run `go test -race ./internal/github ./internal/gitwork -run '^(TestLiveSmoke|TestLiveClientReadOnly|TestLiveBotGitAccess|TestLiveCloneAndPullRequest)$' -count=1`. Keep `-count=1` so Go does not reuse a cached result. These tests read GitHub through REST, read-only GraphQL queries, SSH authentication, and Git fetches without changing GitHub state. The Git checkout test skips unless `repository_url` is exactly `https://github.com/linkdata/miniontesting` (no trailing slash) and `pull_request_number` is set.

Stop any running minion service before a write run so it cannot accept the test invitation or act on test events. ## Usage reports

The service starts recording usage after command validation, duplicate-reply checks and attempt-ID creation, before action preparation. Later failures and retries are recorded; earlier failures can return without a usage record. Reports are local and need no GitHub or AI authentication or network access. They can run while the service is running:

```sh
# Group by repository, invoking user, and action (the default).
./bin/minion usage -config ./config.local.json

# October usage for one repository and invoking user.
./bin/minion usage -repo example-owner/example-repo -user example-user -from 2026-10-01 -to 2026-11-01

# Daily totals by repository.
./bin/minion usage -group-by day,repo

# Export attempts with model, effort, outcome and source URL.
# Executor and source commit are present when a model call was recorded.
./bin/minion usage -group-by none -json > usage.json

# Read records directly if configuration is unavailable or invalid.
# This relative default path assumes the config file is in the current directory.
./bin/minion usage -dir ./var/usage -group-by month,user -json
```

Both the service and the usage command default to `config.local.json` when `-config` is omitted. `-repo` and `-user` match case-insensitively. `-from` is inclusive and `-to` is exclusive; both filter the attempt's start time. Dates use midnight UTC, and RFC3339 timestamps are also accepted. When both are supplied, `-from` must be strictly earlier than `-to`. `-group-by` accepts a comma-separated combination of `repo`, `user`, `action`, `day`, and `month`; day and month groups use UTC. Use `none` for one row per attempt. JSON includes the applied filters, grouped summaries or individual attempts, and overall totals.

Reports combine both providers and all main/critic rounds, track `succeeded`, `failed` and `running` attempts, and count incomplete usage. Per-attempt JSON (`-group-by none -json`) also includes main/critic models and efforts. Dispatched calls include the parent-pinned executor and source commit; `usage_source=executor_reported` marks a saved returned usage claim. Returned-call token counts and completion flags are executor-reported claims, not verified billing. Codex recovers root/helper session counters; Claude uses the CLI's native per-model `modelUsage` totals. Each resumed call records its new invocation's usage without recounting earlier calls; this still includes prior context used in new requests, including cache reads. Claude input includes uncached input, cache creation and reads; its cached-input counter counts cache reads only, excluding creation. **Cached input is a subset of input**: total tokens are input+output, not input+cache+output. Missing, damaged or oversized provider accounting logs/records can leave incomplete saved counts; an incomplete attempt showing zero tokens was not necessarily free. A damaged local usage JSON file makes `minion usage` fail and name the file. Oversized Codex rollout lines are skipped to recover later counters. Recovery uses the live action context, with no fresh budget after cancellation. If already canceled before recovery, retained stream counters can be zero/incomplete despite counters on disk; bounded post-stop recovery remains [#97](https://github.com/linkdata/minion/issues/97) work. Application validation failure does not invalidate an already completed call's accounting.

Records contain metadata/counts, not prompts/replies. A `running` attempt can remain after a crash, hard kill, panic or failed final save. Graceful cancellation records `failed`. A pre-call checkpoint records dispatch intent; cancellation there can leave an incomplete call count without proving a charged request. Retries are separate attempts.

Records are stored in a `usage/` directory beside `state_path` (`var/usage/` relative to the config file's directory by default), independently of notification state. Keep this directory to retain usage history. On Unix, usage saves require directory fsync support for `usage/` and its parent. On Windows, Minion syncs the record before replacement but cannot sync directory metadata; crash durability remains best effort. `-config` loads and validates the local configuration but does not run service preflight; `-dir` bypasses configuration entirely and cannot be combined with `-config`. A missing usage directory produces an empty report.

## Why polling

GitHub does not offer a webhook for a user account's personal mentions. The [notifications API](https://docs.github.com/en/rest/activity/notifications?apiVersion=2022-11-28) is the simplest route for a dedicated machine user: a paginated poll for each whitelisted repository, no public server, and no repository webhook administration. This service requests read and unread participating notifications since a durable cursor for each repository, obeys `X-Poll-Interval`, then inspects content in whitelisted threads. Notification `reason` is thread-level, so the service validates the actual command in each new body/comment and deduplicates by source item plus command, not by notification ID.

Initial issue and pull request descriptions and their comments, pull request reviews and line comments are scanned. Edits to an old issue or pull request description are not treated as new commands, because REST `updated_at` also changes for unrelated thread activity. GitHub notification delivery settings still control what reaches this account. Discussions are unsupported because [their notification subjects can have no URL](https://github.com/orgs/community/discussions/62728), leaving no reliable thread ID. If you later need guaranteed coverage of every edit, discussion support, or lower latency, install repository or [GitHub App webhooks](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks) for the relevant events. A GitHub App posts as its own app bot identity, rather than the configured bot account.

The service stores no access token on disk. `var/state.json` tracks the account and repository cursors, next poll and invitation-check times, completed command IDs, failed job attempts, pending failed or capacity-deferred threads, pending fix commit records, and at most one selected worker's accepted action. That record binds the request and worker identity to the original runtime deadline; assignment is saved before worker delivery. State replacement syncs the new file before rename. On Linux and macOS, selected-worker startup syncs the state path ancestors, and a directory-sync error while saving acceptance or assignment stops the service; host power-loss durability still depends on the filesystem. Windows does not sync directory metadata, so the supported recovery guarantee there is process restart, not host power loss. Each pending fix record contains its SHA and, when capped, the original round maximum, final-candidate blocker warning and actual full-critic approval. The record is saved before push and supplies those facts to the publication reply. A saved assignment is treated as possibly delivered after restart and is never redispatched; a pull proven undelivered in the running process can release that marker. The accepted action keeps its original deadline. After a model-call acknowledgement in either mode, Minion never repeats the model work. A selected action with a saved complete result can resume publication after restart; an assigned action without such a result remains terminal. If the original command remains unedited and eligible, Minion attempts the fixed failure reply for terminal failures. Edits or later authorization changes can suppress that reply; retained records may need manual inspection of any pushed branch. The account cursor seeds a repository cursor when that repository is newly whitelisted. If a repository notification poll fails, only its cursor stays in place; the other repositories and pending retries continue. A repository with more than 2,000 notifications in one poll fails closed at 20 pages, preserving its cursor for intervention. A failed thread is retried from its original scan time with backoff up to 64 minutes while the cursor continues past other notifications. A permanently inaccessible thread remains in the pending list and is logged with its URL; an operator can remove that entry after checking it for valid commands. Generated code changes are pushed to branches for requesters to turn into pull requests.
